3.2 - Almacenamiento de objetos

Buckets y objetos

El almacenamiento de objetos guarda archivos (objetos) dentro de contenedores llamados buckets. No es un disco ni una base de datos: es como una carpeta infinita en internet, barata y duradera.

Durabilidad de 11 nueves (99.999999999%): pierdes un archivo cada... casi nunca. Es donde aterrizan los datos antes de procesarse.
CAP 3 - 3.2 OBJETOS
3.2 - En la practica

Subir y leer, en las dos nubes

GCP - Cloud Storage


from google.cloud import storage

cli = storage.Client(project="mi-proyecto")
bucket = cli.bucket("mi-data-lake")

# subir
blob = bucket.blob("entrada/ventas.csv")
blob.upload_from_filename("ventas.csv")

# leer
blob.download_to_filename("copia.csv")

AWS - S3 (boto3)


import boto3

s3 = boto3.client("s3")

# subir
s3.upload_file("ventas.csv",
               "mi-data-lake",
               "entrada/ventas.csv")

# leer
s3.download_file("mi-data-lake",
                 "entrada/ventas.csv",
                 "copia.csv")
Misma idea, distinto SDK. Si entiendes uno, entiendes el otro: subir, leer, listar, borrar.

Data Warehouses

Redshift y BigQuery - SQL a gran escala

3.3 - El data warehouse

Por que no usar una base de datos normal

Una base de datos transaccional (como MySQL) es buena para muchas escrituras pequenas: registrar un pedido, actualizar un saldo. Pero colapsa al analizar millones de filas.

Un data warehouse esta hecho para lo contrario: leer y agregar cantidades enormes de datos para responder preguntas de negocio.

El truco: almacenamiento columnar.
En vez de guardar fila por fila, guarda columna por columna. Si tu consulta solo necesita 2 de 50 columnas, solo lee esas 2. Menos datos leidos, mas velocidad, menos costo.
CAP 3 - 3.3 DWH
3.3 - La idea clave

Por filas vs por columnas

Por eso un warehouse responde SELECT SUM(edad) sobre millones de filas en segundos: solo toca la columna que pediste.
CAP 3 - 3.3 COLUMNAR
3.3 - BigQuery

BigQuery: serverless de verdad

El warehouse de GCP. Sin servidores ni clusters que gestionar: escribes SQL y Google reparte el trabajo entre miles de maquinas por debajo.

  • Separa computo de almacenamiento
  • Escala automatico e ilimitado
  • Cobra por bytes escaneados por consulta
  • ML integrado con SQL (BigQuery ML)
Para el curso es nuestra base. El sandbox da 1 TB de consultas al mes sin tarjeta de credito. Es lo mas seguro y rapido para que practiquen. GRATIS

3.3 - Redshift

Amazon Redshift: el warehouse de AWS

Columnar, basado en PostgreSQL, muy maduro. Tradicionalmente trabaja con clusters de nodos que tu dimensionas (aunque ya hay version serverless).

  • Excelente si ya vives en el ecosistema AWS
  • Integra con S3, Glue, SageMaker
  • Redshift Spectrum consulta datos directo en S3
En el curso lo veras como demo. Redshift no tiene un sandbox gratuito comodo como BigQuery, asi que el instructor lo mostrara en vivo. DEMO

CAP 3 - 3.3 COMPARATIVO
3.4 - Criterio de seleccion

Como elegir, sin marketing

  • Donde vive tu empresa. Si ya esta en AWS, Redshift reduce friccion. Si en GCP, BigQuery.
  • Quien lo va a operar. Sin equipo de infraestructura, serverless (BigQuery) gana.
  • Patron de uso. Consultas esporadicas: pago por consulta. Uso 24/7 constante: capacidad reservada puede salir mas barato.
  • Madurez del ecosistema. Integraciones, comunidad, talento disponible.
No hay "el mejor". Hay el adecuado para tu contexto. Saber justificar la eleccion es lo que se evalua en este capitulo.

Optimizacion

Particionado, clustering y SQL que no quiebra

3.5 - Particionado

Particionar: divide y vencerlas

Particionar = dividir una tabla grande en fragmentos por una columna, casi siempre fecha. La consulta solo lee la particion que necesita.

Recuerda el arbol del Cap 2: una tabla particionada es un arbol. Filtrar por fecha baja por una sola rama. 

-- BigQuery: tabla particionada por dia
CREATE TABLE ventas
PARTITION BY DATE(fecha_venta) AS
SELECT * FROM datos_crudos;

-- Esta consulta solo lee 1 dia,
-- no toda la tabla:
SELECT SUM(total)
FROM ventas
WHERE fecha_venta = '2025-06-08';
CAP 3 - 3.5 PARTICIONADO
3.5 - Clustering / Sort keys

Clustering: ordenar para buscar rapido


-- BigQuery: ordena dentro
-- de cada particion
CREATE TABLE ventas
PARTITION BY DATE(fecha_venta)
CLUSTER BY region, producto AS
SELECT * FROM datos_crudos;

Dentro de cada particion, el clustering ordena fisicamente los datos por las columnas que mas filtras. Es el primo del Cap 2: datos ordenados habilitan busqueda rapida.

En Redshift esto se llama sort keys. Misma idea: ordenar para que la consulta salte lo que no necesita.
Particionar + clusterizar bien puede convertir una consulta de dolares a centavos.

CAP 3 - 3.5 SQL
3.5 - El antes y despues

La misma respuesta, distinto costo

Caro: escanea todas las columnas


SELECT *
FROM ventas
WHERE fecha_venta = '2025-06-08';
-- lee las 50 columnas de ese dia

Barato: solo lo necesario


SELECT region, SUM(total)
FROM ventas
WHERE fecha_venta = '2025-06-08'
GROUP BY region;
-- lee 2 columnas, 1 particion
Ambas responden sobre el mismo dia. La segunda puede escanear una fraccion de los bytes. En una tabla de terabytes, esa diferencia se nota en la factura.
